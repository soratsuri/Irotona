# Windows x64 release guide

Public releases must be built from the independent soratsuri/Irotona repository after its contents have been reviewed. Never transfer history from the private development repository. The v0.2.0 executable built from private commit 3f14e77a7b261f7e098cc07cb243b5c20622f8d7 corresponds to the application sources in this tree; these repository metadata updates do not change the runtime application source.

Irotona starts with candidate **0.2.0**, based on upstream v0.1.3. A first release in the 0.x series communicates that the modified app is still early. Choose **1.0.0** if the maintainer wants to declare a stable first release. Set the final version before tagging and verify all version sources together.

The supported download is the portable **Irotona.exe**. The internal Cargo binary and Tauri identifier remain unchanged, preserving the existing single-instance identity and settings/session location. Settings and pairing stay beside the running EXE. MSI requires maintaining Windows Installer packaging and testing upgrades. NSIS offers a more flexible setup flow but also needs install, upgrade, and uninstall testing. The existing Tauri bundle configuration keeps both available for separate testing if there is demand. The default distribution includes the portable EXE.

The production app and tray icons come from the selected design in `src-tauri/icons/irotona.svg`. Regenerate the Tauri platform assets with `npm run tauri -- icon src-tauri/icons/irotona.svg --output src-tauri/icons`. The generated `32x32.png` is also embedded as the system-tray icon.

## Build and stage

Use PowerShell 7, Node.js, the Windows x64 Rust MSVC toolchain, and Visual Studio C++ Build Tools. Install the WebView2 Runtime to run the app. Work from a clean checkout. For a version change, update package.json, both version entries for the app in package-lock.json, src-tauri/Cargo.toml, the app entry in src-tauri/Cargo.lock, and src-tauri/tauri.conf.json.

From the repository root, run the existing tests and build commands. Choose a new build and staging directory inside the ignored src-tauri/target tree for each release candidate.

```powershell
$version = (Get-Content package.json -Raw | ConvertFrom-Json).version
npm ci
npm run release:check -- "v$version"
npm test
cargo check --manifest-path src-tauri/Cargo.toml --locked
cargo test --manifest-path src-tauri/Cargo.toml --locked
cargo fetch --manifest-path src-tauri/Cargo.toml --locked --target x86_64-pc-windows-msvc

$env:CARGO_TARGET_DIR = Join-Path $PWD "src-tauri/target/candidate-$version-build"
$cargoRoot = if ($env:CARGO_HOME) { $env:CARGO_HOME } else { Join-Path $env:USERPROFILE '.cargo' }
$env:CARGO_ENCODED_RUSTFLAGS = @("--remap-path-prefix=$cargoRoot=/cargo", "--remap-path-prefix=$PWD=/source") -join [char]31
npm run tauri build -- --no-bundle -- --locked
./scripts/stage-release-assets.ps1 -Version $version -Destination "src-tauri/target/candidate-$version-assets"
```

Stop if any command fails. The Rust flags replace local paths in the executable. The staging script checks the Windows x64 PE and version and creates a fresh directory. It produces the following assets.

- **Irotona.exe** is the unsigned portable executable.
- **LICENSE** and **NOTICE** contain the GPL terms and project attribution.
- **Irotona-<version>-source.zip** contains the exact committed application source in app/, the original crates.io source packages for the locked Windows x64 dependency graph in rust-crates/, and their declared licenses in rust-dependencies.tsv. Each source package retains its original files. To build the app from the archive, extract it, enter app/, and run the build commands through the Tauri build step. npm and Cargo resolve the pinned packages using the included lockfiles.
- **SHA256SUMS.txt** lists the SHA-256 of each of those four files.

Check the names, sizes, hashes, source ZIP contents, and crate licensing before distributing. For source availability, attach the full corresponding-source ZIP alongside the EXE with the same access. GitHub's generated source ZIP contains the repository tree only. [GPLv3, section 6](https://www.gnu.org/licenses/gpl-3.0.html#section6)

## Before the first public release

1. Review all Git refs and reachable history for credentials, emails, screenshots, and personal paths. Review GitHub releases, issues, pull requests, and attachments separately. Resolve any exposure or rights concern before changing visibility.
2. Check dependency licenses and bundled asset provenance. The Rust inventory includes MPL-2.0, Unicode-3.0, BSD and other permissive terms. Preserve the original notices. The canvas weave texture is generated by `scripts/generate_matte_canvas.py` (optional Python packages) and the fine-art paper texture by `scripts/generate_fine_art_paper.py` (Python standard library only); neither is an app runtime dependency. Check the generated PNGs against their generators before release. Verify the icon outputs against `src-tauri/icons/irotona.svg` and review any other images included in the public tree.
3. Test the actual staged EXE on Windows 11 x64 with a separate writable folder and a test CSP environment. Cover launch, tray exit, settings persistence across restart, pairing, reconnect, both drawing color slots, pen drag/release, palette shortcuts, pinning and eyedropper refresh. Record the Windows, WebView2 and CSP versions and artifact SHA-256.
4. Review the pull request workflow's portable artifact from the intended main commit. Compare its contents and hashes with the artifact you tested if you plan to publish the CI build.

Once the version and public release are authorized, tag the reviewed main commit with an annotated vMAJOR.MINOR.PATCH tag and push that tag. The existing tag workflow checks the locked version and tests, stages the five assets, and creates a **draft**. Review the draft title, notes, artifacts and source access before manually publishing. If draft creation fails, inspect any existing draft and its assets before retrying. Keep the tag and published assets tied to the tested commit.
